**Auditoria de desempenho do Lume/K5 — 22 de setembro de 2026**

O carregamento mobile precisa de atenção principalmente no Lume e no Início. O Lume apresentou LCP mediano de **6,13 s**; o Início, **5,23 s**. Há também dois problemas de layout confirmados: a abertura do histórico desloca o chat em desktop e o grid do Início ultrapassa a largura da tela no celular.

Esta entrega é uma auditoria. As alterações propostas abaixo foram verificadas por leitura do código, cobertura de JavaScript, traces e experimentos temporários no navegador; não foram aplicadas aos arquivos da aplicação.

**Ambiente e método.** Commit `99ef9a8`, árvore inicialmente limpa, Node 26.6.0, pnpm 12.4.2, Next.js 16.3.5 com Turbopack, React 19.2.8 e Tailwind CSS 4. A aplicação foi preparada com `pnpm db:setup`, compilada com `pnpm build` e servida por `pnpm --filter @k5/web start` em `http://localhost:3000`. Foi reutilizada a conta de validação existente, com os dados locais reais, sem fixtures de desempenho.

Não havia ferramentas do Chrome DevTools MCP disponíveis. A coleta equivalente usou Lighthouse **13.5.0**, Playwright **1.63.0** e Chromium **153.0.8010.12**, em navegador separado. Foram salvos **22 relatórios Lighthouse e 22 traces**, entre 09:31 e 09:35, horário de Brasília, além de inspeções posteriores de DOM, rede e acessibilidade.

- Mobile: três navegações por rota, cache HTTP, Cache Storage, service worker e localStorage limpos antes de cada medição; cookies de autenticação preservados. Perfil Lighthouse de 412 × 823, RTT simulado de 150 ms, 1.638,4 Kbps e CPU 4× mais lenta.
- Desktop: uma navegação por rota; três para o Lume, para confirmar o CLS. Perfil padrão do Lighthouse, RTT simulado de 40 ms, 10.240 Kbps e CPU 1×.
- Inspeção adicional: 390 × 844 e 1440 × 900, sem limitação artificial de rede/CPU. Dez árvores de acessibilidade e 494 respostas de rede, incluindo interações.
- Os valores abaixo são de laboratório. A primeira rodada também inclui alguns carregamentos iniciais de módulos do servidor. As repetições aquecem o servidor e voltam a limpar o cache do navegador.

No Lume, o chunk `1vhoq5_gr4bup.js` contém o runtime do assistente e componentes associados: aproximadamente **189 KiB transferidos**, dos quais **122 KiB** ficaram sem execução no carregamento. Isso indica oportunidade de adiar funcionalidades, não que a biblioteca inteira possa ser removida. [AgentChat](../apps/web/src/components/agent-chat.tsx) importa painel de fontes, busca de modelos e seus componentes de interface de forma estática. Carregar esses painéis na primeira abertura é uma fronteira concreta a avaliar.

A conversa também depende da sequência hidratação → `/api/conversations` → `/api/conversations/:id` → mensagens. O código está em `agent-chat.tsx`, linhas 603 e 622. Para uma conversa conhecida, entregar os dados iniciais autorizados pela página pode encurtar essa sequência. Preservar a seleção de modelo, streaming, histórico e verificação de acesso por usuário/escritório. Nenhuma chamada de geração de IA foi disparada nesta auditoria.

O CLS do chat decorre da diferença entre `serverListOpen()` retornar `false` e `readListOpen()` abrir o histórico automaticamente em desktop. O `<aside>` introduzido depois ocupa `md:w-72`. No Início, [command-center.tsx](../apps/web/src/components/command-center.tsx), linhas 31–49, aguarda tarefas, reuniões, clientes, casos e conversas antes de atualizar todas as seções. Esses tempos explicam a ordem das dependências; **não devem ser somados ao LCP simulado de 5,23 s**. O CSS global `3-ex3idsz81lo.css` tem **97.630 bytes descomprimidos**, cerca de **16,7 KiB transferidos**. O Lighthouse estima aproximadamente **300 ms de impacto bloqueante** no mobile. Isso é secundário frente ao JS e à fonte sem uso. A auditoria de CSS não utilizado apontou **zero economia**, portanto não há evidência para recomendar remoção de regras ou outra ferramenta de purge.

Todos os recursos observados vieram de `localhost`; não há origem externa ou preconnect a eliminar nas páginas medidas. Não houve resposta HTTP 4xx/5xx nas 494 respostas inspecionadas. Nenhuma imagem raster compôs o carregamento principal, portanto não há recomendação de conversão de imagens para WebP nesta auditoria.

JS e CSS chegam com gzip; arquivos com hash usam `Cache-Control: public, max-age=31536000, immutable` e ETag. WOFF2 já é comprimido. As páginas autenticadas usam `private, no-cache, no-store, max-age=0, must-revalidate`. O comportamento de cache das páginas privadas deve ser preservado. Não foi identificado ganho que justifique trocar compressão ou relaxar cache de autenticação neste ambiente.

O tempo de resposta do documento nas rodadas com servidor aquecido ficou entre **9 e 40 ms** no diagnóstico `server-response-time`; isso não mede latência de infraestrutura remota. Os prefetches RSC foram identificados, mas nenhum ganho isolado foi medido ao desativá-los. Não se recomenda removê-los indiscriminadamente. Os polyfills de compatibilidade apontados pelo Lighthouse representam cerca de 13 KiB, com ganhos pequenos ou nulos conforme a rodada; têm prioridade inferior aos chunks identificados acima.

**Acessibilidade e interação.** A análise automática retornou 100 na entrada, 95 no Início mobile, 90 no Lume mobile, 95 no Cofre mobile e 96 na Agenda mobile. Esses números não constituem certificação de acessibilidade.

- O token `--subtle-foreground: #93938e`, em [globals.css](../apps/web/src/app/globals.css), linha 31, produz contraste **3,08:1** sobre branco. É usado em texto de 11 px da navegação mobile e 13 px do Cofre; o mínimo aplicável é **4,5:1**. No item selecionado do histórico, sobre `#ebebe8`, o contraste caiu para **2,58:1**. Usar um token de texto com contraste suficiente nesses elementos e conferir ambos os temas. [WCAG 2.2 — contraste mínimo](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).
- O input de arquivo em [agent-chat.tsx](../apps/web/src/components/agent-chat.tsx), linha 332, usa `sr-only` e não tem nome acessível. Adicionar uma label, por exemplo `aria-label="Arquivo para anexar"`.
- O seletor de modelos, linha 242, tem `aria-label="Selecionar modelo"`, mas o texto visível mostra o modelo selecionado. Incluir esse texto no nome acessível, por exemplo `aria-label={\`Selecionar modelo: ${selected?.modelId ?? 'Modelo'}\`}`.
- Nas dez árvores não foram encontrados IDs duplicados ou referências quebradas de `aria-labelledby`/`aria-describedby`. Não ocorreram erros de JavaScript de página.
- O menu Mais manteve foco dentro do diálogo durante o teste e devolveu o foco ao botão após Escape. No Início, o teste por ponteiro falhou com o overflow; por teclado funcionou, e o experimento de grid corrigiu o clique.
- O painel Fontes fechou com Escape após a transição de saída, confirmado em teste específico. As trocas Agenda → Tarefas funcionaram em desktop e mobile. Não foram auditados todos os percursos de teclado, contraste do tema escuro ou fluxos extensos de edição.

**Achados do código e próximos pontos de implementação.** O build usa Turbopack, com divisão automática por rota e JavaScript minificado. Não havia source maps nos chunks públicos gerados. Bibliotecas de processamento de documentos estão em `serverExternalPackages`; não apareceu evidência de OCR ou PDF.js nos chunks iniciais examinados que justificasse mudar essa configuração.

O Início importa `agendaCall` e `localDate` de [agenda-forms.tsx](../apps/web/src/components/agenda-forms.tsx). Esse módulo também importa editor, Dialog e `localInstant`, que utiliza `@js-temporal/polyfill`. O chunk `2dp1ai52r2wlv.js`, contendo Temporal e componentes de formulário, chega ao Início e à Agenda com cerca de 47,8 KiB transferidos; a cobertura do carregamento deixa aproximadamente 39,3 KiB sem execução. Separar helpers e editor permite experimentar carregamento sob demanda sem retirar as regras de datas civis e fusos.

Exemplo de estrutura proposta, após extrair `agendaCall` para um módulo próprio:

```tsx
import dynamic from 'next/dynamic';
import { localDate } from '@/lib/calendar-days';
import { agendaCall } from '@/lib/agenda-client'; // módulo proposto

const AgendaEditor = dynamic(() =>
  import('./agenda-forms').then((module) => module.AgendaEditor)
);

// Renderizar o editor apenas quando o estado de abertura estiver ativo.
```

Outro chunk compartilhado, `2y0q5yp5nixye.js`, contém Zod e teve aproximadamente 94% sem execução durante a carga. A validação continua necessária: a análise indica rever os imports e o catálogo carregado, não remover validação. [webmcp/adapter.ts](../apps/web/src/lib/webmcp/adapter.ts) combina transporte HTTP, catálogo completo de capabilities e geração de JSON Schema. Avaliar fronteiras que carreguem somente os contratos necessários à tela, mantendo a mesma autorização no servidor.

[agenda-workspace.tsx](../apps/web/src/components/agenda-workspace.tsx), linhas 80–95, carrega todos os clientes em páginas sequenciais de 100 para preparar filtros e editor. Essa dependência é confirmada no código, mas o ambiente medido tinha poucos dados; impacto com escritórios grandes **não foi quantificado**. Considerar seleção pesquisável/paginada e preparação do editor na abertura. Os timers de 150 ms também se aplicam à primeira busca; separar a carga inicial do debounce de digitação é uma oportunidade de menor alcance, ainda sem experimento isolado.

O build passou em cerca de 46 s. Emitiu avisos de file tracing em [storage/index.ts](../apps/web/src/lib/storage/index.ts), sugerindo que paths dinâmicos podem ampliar o pacote do servidor, e aviso do cache do Turborepo sobre um link de `mammoth` no Windows. Não são falhas do build nem causas comprovadas do LCP. Antes de alterar tracing, medir o pacote e preservar exclusões de `.data` e `.env`.

O [README do app](../apps/web/README.md) afirma que a interface usa fontes do sistema. O código atual usa `next/font/google` para gerar fontes locais; atualizar essa descrição em uma futura mudança de documentação evitará confusão sobre rede e requisitos de build.
